# AI Manga Editorial Meeting — 改訂版設計書

## ハッカソン提出用 skill 設計 v2.0

---

## 1. コンセプト（一言）

**漫画の企画メモを渡すだけで、AI編集者たちが勝手に会議を開いて、掲載判断まで出してくれる。**

情報が足りなければ自分で推測し、自信がなければ調べに行き、判断に迷えば自分で見直す。
ユーザーは何もしなくていい。会議が終わるのを待つだけ。

---

## 2. 審査基準への対応設計

### 自律性 40% — 「不完全な入力でも最後まで走りきる」

**核心：ユーザーが雑に渡しても、エージェントが自分で考えて完走する。**

| 自律性の要素 | 実装方法 |
|---|---|
| 最後まで進められる | 6フェーズの自動進行。各フェーズの出力が次のフェーズの入力になるパイプライン |
| エラーから立て直す | 情報不足を検知 → 企画文から推測して仮置き → 仮置きであることを明示して続行 |
| 足りない情報を調べる | 類似作品・ジャンルトレンドをWeb検索。検索結果が的外れなら別クエリで再検索 |

**デモシナリオ（最重要）：**

```
ユーザー入力（あえて不完全）:
「タイトル：炎の錬金術師
 コンセプト：禁じられた錬金術で妹を救う少年の旅」

→ たったこの2行から、エージェントが：
  1. 主人公の性格・弱点を企画文から推測
  2. 対立キャラが未定義 → ジャンルの定石から仮設定
  3. 第1話の構成が不明 → コンセプトから逆算して仮構成
  4. 各軸を分析（推測部分は「⚠ 推測」マーク付き）
  5. 類似作品をWeb検索して評価根拠を補強
  6. セルフレビューで判断を再検証
  7. 最終レポートを出力
```

**これで「2行渡しただけで全部やってくれた」が動画に映る。**

### クオリティ 35% — 「漫画家が次にやることがわかる」

最終出力を「編集会議レポート」として構造化する。

```
出力：編集会議レポート
├── 企画サマリー（入力＋推測で補完した全体像）
├── 4軸スコア＋根拠
│   ├── 主人公エンジン：7/10 — 根拠と具体的指摘
│   ├── 対立構造：6/10 — 根拠と具体的指摘
│   ├── 読者フック：5/10 — 根拠と具体的指摘
│   └── 連載エンジン：4/10 — 根拠と具体的指摘
├── 改善アクションリスト（優先度順）
│   ├── 1. 連載エンジン：敵の階層を3段に設計せよ
│   ├── 2. 読者フック：第1話に「謎」を1つ仕込め
│   └── 3. 対立構造：ライバルキャラを追加せよ
├── 参考作品（Web検索結果から）
│   ├── 「鋼の錬金術師」— 敵組織階層化の参考
│   └── 「ブラッククローバー」— ライバル構造の参考
├── 掲載判断：条件付き通過 / 保留 / 却下
└── ⚠ 推測箇所の一覧（ユーザーが後で修正可能）
```

### インパクト 25% — 「作って、育てて、共有する」

| テーマ | 実装 |
|---|---|
| 作って | 企画を投げると編集会議レポートが「作られる」 |
| 育てて | 同じ企画を修正して再投入 → 前回との差分比較「前回: 4/10 → 今回: 7/10 ✅ 改善」|
| 共有する | レポートのMarkdownエクスポート。他の人が同じskillで自分の企画を回せる |

## 3. エージェント構成（実装設計）

### フェーズ設計

```
Phase 1: Input Parser（入力解析）
  └ 企画テキストを構造化
  └ 欠損フィールドを検出
  └ 欠損があれば文脈から推測して仮埋め（⚠マーク付き）

Phase 2: Structure Analysis（構造分析）
  └ 4つの分析を並列実行
  ├ Character Agent → 主人公エンジン評価
  ├ Conflict Agent → 対立構造評価
  ├ Hook Agent → 読者フック評価
  └ Serialization Agent → 連載エンジン評価

Phase 3: Evidence Search（根拠調査）
  └ スコアが低い軸について類似成功作をWeb検索
  └ 検索結果が不十分なら別クエリで再検索（リトライ）
  └ 成功パターンを抽出して改善提案の根拠にする

Phase 4: Editorial Judge（掲載判断）
  └ 4軸スコアを総合して掲載判断
  └ 判断ロジック：
     - 全軸6以上 → 掲載
     - 1軸でも3以下 → 却下
     - その他 → 条件付き通過 or 保留

Phase 5: Self Review（セルフレビュー）
  └ 判断の再検証
  └ 各スコアの根拠と判断の整合性チェック
  └ 矛盾があればスコア修正
  └ 推測で仮埋めした部分が判断に影響していないか確認

Phase 6: Report Generation（レポート生成）
  └ 全分析結果を構造化レポートとして出力
  └ 改善アクションリストを優先度順に生成
  └ 推測箇所の一覧を付記
```

### 自律性が発動するタイミング（デモで見せるべきポイント）

```
★ 見せ場1：不完全入力への対応（Phase 1）
  「対立キャラの記述がありません。
   コンセプトから推測します…
   → 禁術を取り締まる勢力の存在を仮定。
   ⚠ この要素は推測です。」

★ 見せ場2：Web検索による根拠補強（Phase 3）
  「連載エンジンのスコアが低いため、
   同ジャンルの成功作を調査します… 🔎
   → 検索: "ダークファンタジー 少年漫画 連載 成功"
   → 結果不十分。クエリ変更して再検索…
   → 検索: "錬金術 漫画 長期連載 構造"
   → 成功パターン検出：敵組織の階層化が有効。」

★ 見せ場3：セルフレビューの割り込み（Phase 5）
  「判定を再検証します。
   読者フック 4/10 の根拠を確認…
   → 主人公の過去に伏線が機能する可能性を検出。
   → 読者フック: 4 → 5 に修正。
   掲載判断への影響：保留 → 条件付き通過に変更。」
```

### 実装の核心：system.md のエージェントオーケストレーション

skillの本体は1つのシステムプロンプト。
Claude自身が6フェーズを順に実行し、各フェーズの出力を次のフェーズに渡す。
マルチエージェントではなく、**1つのプロンプト内でロールを切り替える設計**。

理由：
- skill提出物として最もシンプル
- 外部APIやフレームワーク依存なし
- Claude Code / claude.ai でそのまま動く
- デバッグしやすい

### Web検索の活用

```
Phase 3（Evidence Search）で以下を実行：
1. スコアが6未満の軸を特定
2. その軸に関連する検索クエリを自動生成
3. Web検索ツールで調査
4. 結果が不十分なら最大2回リトライ（クエリ変更）
5. 成功パターンを抽出して改善提案に組み込む
```

### 「育てる」の実装

```
再投入時の差分比較ロジック：
1. 前回のレポートをユーザーが貼り付ける（or 会話履歴から参照）
2. 今回の分析結果と前回スコアを比較
3. 各軸に「↑改善」「→変化なし」「↓悪化」を付与
4. 「まだ弱い部分」を重点的に指摘
```

## 7. 差別化ポイント

**既存との違い：**

| 既存のAI創作ツール | 本skill |
|---|---|
| ストーリーを「作る」 | ストーリー構造を「壊す（検証する）」 |
| 完全な入力を要求する | 不完全でも自走する |
| 1回の出力で完結 | 修正→再投入で「育てる」 |
| 汎用的なフィードバック | 漫画編集の4軸に特化した構造分析 |

**審査で刺さるフレーズ：**
- 「AIはストーリーを作らない。編集者として構造を壊す側に回る。」
- 「2行のメモから、編集会議が勝手に始まる。」
- 「足りない情報は自分で考え、自信がなければ調べに行き、間違えたら自分で直す。」

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| Web検索結果が的外れ | 最大2回リトライ＋検索失敗時は「調査不能」として続行する設計 |
| セルフレビューが形骸化 | 「修正なし」の場合も根拠を明示させる。修正率が0%にならないよう評価基準に幅を持たせる |
| 推測が的外れ | 推測箇所は全て⚠マーク。レポートの最後に「推測一覧」として列挙し、ユーザーが修正可能 |
| プロンプトが長すぎて精度低下 | 各フェーズのプロンプトを分割し、フェーズごとにフォーカスを絞る |
| 2週間で間に合わない | MVP = Phase 1-4 + レポート出力。Phase 5（セルフレビュー）は後回し可能。ただし自律性スコアは下がる |
